<objective>
Three queue fixes that build on quick task 261015-h0q (commits 4b575ed, 5598347, e18a177):

1. **Run-wide abort.** When the tool accepts an operator Abort, the aborted run's remaining queued
   steps also leave the queue. Until now only the aborted step did.
2. **T-01-08 closed.** The late-reply path only removes the exact aborted attempt. Today
   `CommandQueue._recordAcceptedAbort` removes the step's queue row unconditionally. Because
   `SqliteQueue.gotoCommand` and `gotoCommandByIndex` re-queue the same `queue_id`, a slow abort
   reply can delete a re-queued or re-running attempt. With run-wide removal, the same reply
   could delete the whole run.
3. **No orphan re-dispatch after a restart.** A step left STARTED by a previous galago-web process
   is never dispatched again on the next queue start.

Purpose: the operator decides every recovery action, and the queue never acts on its own. An
accepted abort means "this run stops here". A stale reply must not override a later operator
re-queue or restart. A restart must not re-send a physical step whose real-world outcome is
unknown.

Output: changes to SqliteQueue and CommandQueue, updated and new Vitest coverage (including the
queue_id-reuse race and a real two-instance restart on one DB file), and T-01-08 closed in the
Phase 1 SECURITY.md.

Planner decisions (no CONTEXT.md exists for this quick task; these are resolved from the code at
planning time):
- **Remaining steps of an aborted or interrupted run become SKIPPED** and leave `<q>_queue`. Only
  rows still in `<q>_queue` with the same `run_id` are touched. Of those, only CREATED rows change
  status; a row in any other state keeps its status and is just dequeued. Records are kept.
  Reasons for SKIPPED: it is an existing status that renders greyed with the skip icon. The run
  still shows FAILED, because `controller/components/runs/utils.ts` getRunAttributes checks for a
  FAILED step first. gotoCommand and gotoCommandByIndex can still re-queue the run. No new
  RunStatus value is added, same reasoning as 261015-h0q.
- **Orphan disposition after a restart.** The orphan becomes FAILED with an "interrupted by
  restart" error and is dequeued, together with its run's remaining queued steps (the same
  run-wide primitive as abort). The instrument's state after an interrupted step is unknown, so
  automatically running the next step of that run would be the queue acting on its own. Other
  runs are untouched. The operator can re-queue from the swim lane.
- **T-01-08 gate is three layers**, evaluated with no await between them:
  - (a) `_runningStep === step` → only set the busy-loop marker (unchanged).
  - (b) `_failedAttempt === step`: the aborted attempt's frozen snapshot is still the latest
    ended attempt, and no restart, goto or new attempt has happened since.
  - (c) one SQLite transaction re-checks that the row exists, `run_id` matches, status is
    FAILED and the row is still in `<q>_queue`.

  Any operator queue action after the attempt ended (restart, gotoCommand, gotoCommandByRunIndex)
  supersedes a pending stale reply. Skip and clear are caught by layer (c).
- **Out of scope**, so do not change any of these:
  - The pending todo `.planning/todos/pending/2026-10-15-queue-errors-item-not-found-after-clear-during-abort.md`
    stays open. failAndDequeueRun throws the same "Item N not found" that fail does when the row
    was deleted mid-run.
  - A step that succeeds after an accepted abort: unreachable for the only runControl tool. The
    F.A.S.T. core refuses abort outside running or paused, and an aborted run replies
    ERROR_FROM_TOOL (`vendor/galago-tools/tools/fast/server.py` lines 116 and 813-830).
  - Concurrent double `_start` (pre-existing).
  - `vendor/galago-tools` (submodule).
</objective>
