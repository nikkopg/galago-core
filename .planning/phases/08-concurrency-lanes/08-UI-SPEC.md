# Phase 8 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> Mode: `--auto`. No questions were asked. Locked inputs: `08-CONTEXT.md` (D-01..D-27), `08-RESEARCH.md` (static-scan pin matrix, seams, Pitfalls P-1..P-9), `06-UI-SPEC.md` and `07-UI-SPEC.md` (this phase extends their tokens, type scale and copy conventions), and the existing run-page components in `controller/components/runs/`. Every other open choice took the option most consistent with those and is listed under "Auto Decisions".
> Scope (seven surfaces): S1 `CommandDetailsDrawer` Lane input, "Wait for all earlier steps" switch and inert-flag note (D-18). S2 `ProtocolDetailView` preview and visual lane summary, plus the run-creation refusal copy (D-17, D-20, D-23, D-25, D-26). S3 Start confirmation per-lane listing (D-20). S4 `SwimLaneComponent` per-lane rows (D-21). S5 new `LanesPanel` with the Freeze lanes button, its confirm and the "Lanes frozen" indicator (D-15, D-24). S6 error banner failure list (D-16). S7 lane-aware run outcome (D-22, no new visual).
> Safety stance carried into every surface: the interface only ever states what the queue did and what the operator can press. It never preselects a physical decision, never auto-acknowledges, retries, resumes or aborts, and a Freeze aborts nothing. Every recovery is the operator's.

## Layout and Interaction Contract

Each new surface has one element the eye lands on first; everything else on the surface is secondary (muted, 12px or 14px regular).

| Surface | Focal point | How it leads |
|---------|-------------|--------------|
| S1 Drawer | The `Lane` field label and input at the top of the new group | First element after the `Divider`; the barrier switch and the notes follow in muted text |
| S2 Preview and summary | The group headers (`Lane {name} · {n} steps`) | 14px/700 on the gray.50 / `surface.panel` header bar; step lines beneath are 12px mono regular |
| S3 Start confirmation | The existing count line (`This Start will run ...`) | Unchanged body line first; the lane lines follow, step lines are caption tone |
| S4 Lane rows | The lane label column (lane name, 14px/700, sticky) | It is the only bold, filled element in the row; timestamps are muted captions |

### S1. CommandDetailsDrawer: Lane controls (D-18, LUI-01)

Placement: inside the existing Advanced Parameters accordion panel, directly after the "Value to Match" `FormControl` and before the existing "Run Asynchronously" row. A `Divider` (`my={4}`) separates the new group from the skip-variable fields above. The group has no heading of its own beyond the two field labels. The dead "Run Asynchronously" switch and its helper sentence stay exactly as they are (D-02).

```
------------------------------------------------------------
Lane                          [ Input  placeholder "primary" ]   <- list="lane-suggestions"
Blank means the primary lane. Lanes in this protocol: primary, fast        (12px muted)
[flag line, only when it applies]                                          (14px warning)

Wait for all earlier steps    [ Switch ]
Runs only after every earlier step on every lane has finished. Use it before a step that
needs the plates in place.                                                  (12px muted)

(i) Lanes take effect only when parallel lanes are enabled on the server.   (14px muted)
------------------------------------------------------------
Run Asynchronously            [ Switch ]       <- unchanged
```

| Aspect | Contract |
|--------|----------|
| Shown for | Tool steps only. A `Tool Box` step shows **no** Lane or barrier control and no empty placeholder (pure predicate in `laneFields.ts`, D-18). |
| Shown when the flag is off | Yes, always. The inert-flag note below is permanent (the client does not know the server flag; there is no client copy of it). |
| Lane input | Controlled `Input`, `placeholder="primary"`, `list="lane-suggestions"`, `autoComplete="off"`, `maxLength={32}`. The value written is trimmed and lower-cased. Blank or `primary` **deletes** the `lane` key (never writes `lane: ""`, Pitfall 24b). |
| Suggestions | A native `<datalist id="lane-suggestions">`: `primary` first, then every distinct lane already used by other steps of this protocol in first-appearance order. At most 4 distinct lanes exist in a run, so at most 4 options. Suggestions never preselect: the field starts blank. |
| Helper line (12px muted) | `Blank means the primary lane. Lanes in this protocol: {list}`. With no other lane used: `Blank means the primary lane. No other lanes are used in this protocol yet.` |
| Barrier switch | `FormControl display="flex" alignItems="center"`, label `Wait for all earlier steps`, `colorScheme="teal"`, controlled `isChecked`. Off **deletes** the `laneBarrier` key (never writes `false`). Born off. |
| Barrier helper line (12px muted) | `Runs only after every earlier step on every lane has finished. Use it before a step that needs the plates in place.` |
| Inert-flag note (14px muted, `InfoIcon` aria-hidden before the text) | `Lanes take effect only when parallel lanes are enabled on the server.` |
| Read-only drawer (run page, `isEditing` false) | Both controls render **disabled** with the saved values (same `isDisabled={!isEditing}` rule as the other advanced parameters). The datalist is not rendered. The note stays. |
| Save | Unchanged: `Save Inputs` writes the advanced parameters. Nothing here blocks saving; the server (`validateLanes`) is the final check at run creation (Phase 7 precedent: "Saving is not blocked"). |

Inline flags (14px warning, `WarningTwoIcon` aria-hidden before the text, under the Lane input, first match wins, all text):

| Condition | Flag copy |
|-----------|-----------|
| Lane name does not match `[a-z0-9_-]{1,32}` after trim and lower-case | `Lane name '{v}' is not valid. Use 1 to 32 characters: a-z, 0-9, - and _.` |
| This step's lane would be a 5th distinct lane in the protocol | `This protocol would use {n} lanes. A run can use at most 4.` |
| The same tool is already on a different lane in this protocol | `{tool} is already on lane '{other}'. One tool can use only one lane per run.` |
| This is the first step on a non-primary lane, it is not at position 1, and the barrier is off | `The first step on lane '{lane}' should wait for all earlier steps, so it starts only after the plates are placed.` |

### S2. ProtocolDetailView: preview and visual lane summary (D-20, D-26, LUI-03, LUI-04)

Two renderings, both inside the card that already hosts the protocol, both **absent** when no step carries a non-primary lane (untagged protocols render byte-identical to today).

**S2a. Visual protocols: Lane summary.** Computed client-side from the pure `laneScheduling.ts` module (research: `protocol.preview` is script-mode only). Placed directly below the existing step strip.

```
Lane summary                                                          <- 14px/700
+ Lane primary · 4 steps -------------------------------------------+  <- group header bg gray.50/surface.panel, 14px/700
|  1. [stack] pick plate in                                          |  <- 12px mono
|  2. [stack] pick plate out                                         |
+---------------------------------------------------------------------+
+ Lane fast · 1 step -------------------------------------------------+
|  3. [fast] transfer — waits for all earlier steps                  |
+---------------------------------------------------------------------+
(warnings, if any)  Alert status="warning"
```

| Aspect | Contract |
|--------|----------|
| Group order | Lane order = first appearance in the protocol (D-20). `primary` is labelled `primary`; an untagged step belongs to it. |
| Group header | `Lane {name} · {n} step` / `Lane {name} · {n} steps` (singular for 1). |
| Step line | `{globalPosition}. [{toolId}] {command words}` in 12px mono (the format of the existing script "Generated Commands" list). Global position keeps cross-lane order readable. A barrier step appends ` — waits for all earlier steps`. Tool Box steps are listed under `primary` with their `[Tool Box]` id. |
| Warnings | The same messages `validateLanes` would refuse with at run creation (copy below), in one `Alert status="warning" variant="left-accent"` with one `Text` per message, above-the-summary-footer. No Alert when there are none. |
| Flag | The summary is a description of intent. It does not say whether lanes are enabled on the server (see the S1 note). |

**S2b. Script protocols: Generated Commands.** The existing "Generated Commands (N)" box is unchanged when no command has a non-primary lane. When one does, the same box lists commands grouped under the same group headers and the same step line (`{n}. [{toolId}] {command}` plus the existing params JSON, then the barrier suffix). The 300px max height and scroll stay. `protocol.preview` returns `laneWarnings: string[]`; they render in the same warning `Alert` below the box. With the flag off and lane tags present the server returns exactly one warning (D-26) and the UI shows it verbatim with the first letter capitalised: `Lane tags ignored: parallel lanes disabled`. No other copy is added around it.

**S2c. Run creation refusal (LUI-03).** `validateLanes` messages are rendered **verbatim** by the existing run-creation error path (existing error toast, title unchanged). The message text is part of this contract so server and UI agree; the planner implements it in `laneScheduling.ts`:

| Refusal | Message |
|---------|---------|
| Non-tool step on a secondary lane | `Step {n} ({command}) is on lane '{lane}', but only tool steps can run on a secondary lane. Move it to the primary lane.` |
| One tool on two lanes | `Tool '{tool}' is on lanes '{a}' and '{b}'. One tool can use only one lane per run.` |
| Invalid lane name | `Lane name '{v}' is not valid. Use 1 to 32 characters: a-z, 0-9, - and _.` |
| More than 4 lanes | `This run uses {n} lanes. A run can use at most 4.` |
| First row of a secondary lane has no barrier (D-25, per lane) | `The first step on lane '{lane}' (step {n}) must wait for all earlier steps. Turn on "Wait for all earlier steps" for it.` |
| Tool Box `goto` in a run with a non-primary lane (D-23) | `Step {n} is a Go to step, which cannot be used in a run that has lanes. Remove it, or keep every step on the primary lane.` |
| Setup would never finish (dead wait) | `The lane setup cannot finish: step {n} would wait forever. Check the "Wait for all earlier steps" settings.` |

The S1 inline flags and the S2 warnings reuse these sentences (the S1 flags are the author-time, non-blocking versions).

### S3. Start confirmation: per-lane listing (D-20, LUI-04)

The existing confirm modal (`QueueStatusComponent`, header "Warning", body "Make sure instruments are not unintentionally in simulation mode.") is unchanged. `queuedStartLines` output is **byte-identical for untagged queues**. For a queue whose queued rows include any non-primary lane, `queuedStartLines` appends lines after the existing count lines and before the note line, using the existing line shape (`{ text, tone }`) so the JSX needs no change except mapping tone to style:

| Order | Line | Tone | Notes |
|-------|------|------|-------|
| 1 | `Steps by lane (lane order is the order they first appear):` | body | Appears once. |
| 2 | `Lane {name}: {n} step` / `{n} steps` | body | One per lane, first-appearance order. |
| 3 | `{position}. {toolId} · {command words}` and, for a barrier, ` · waits for all earlier steps` | caption | One per queued step of that lane, under its lane line. Only rows the Start will pick up (CREATED, FAILED). STARTED rows are not listed (the existing "still running" line covers them). Tool names are the stored `toolId`; the Start summary does not fetch tool metadata. |
| last | `Starting clears a lane freeze. Lanes then start again together.` | caption | Only when the lane status says the lanes are frozen (failure, freeze). Omitted otherwise and omitted when lane mode is off. |

- Position is the queue order of the row among the queued rows of the run. Long lists scroll with the modal body; no cap, no truncation (every step the Start will run is named, matching the "Logs list the exact steps" promise).
- Buttons stay "Accept" (teal, existing) and "Cancel" (ghost). Nothing is preselected or auto-confirmed.
- The line order inside one lane follows queue order, so a retried FAILED step appears first, which is true (it is claimed first).

### S5. LanesPanel: Freeze lanes and "Lanes frozen" (D-15, D-24, LAN-09)

New component `components/runs/LanesPanel.tsx`, fed by one new hook `hooks/useLaneStatus.ts` (single reader of `commandQueue.laneStatus`, polled at 1500 ms like `getError`). Mounted in `RunsComponent.tsx` directly **below** `<ControlBar />` and above the Runs List card. It is a `Card` with the same shell as `ControlBar` (`bg` white / `surface.section`, `shadow="md"`).

**Visibility.** The panel renders `null` unless lane mode is on **and** the active run has lane-tagged rows (`laneStatus.laneMode && laneStatus.hasLaneRows`). With the flag off, or an untagged run, the run page DOM is unchanged. While loading or on a failed `laneStatus` read it also renders nothing (it never shows a stale "frozen" or a button that might not work).

```
+ Lanes ------------------------------------------------ [ Freeze lanes ] +
| (A) running      Running now: [fast · F.A.S.T.] [primary · STACK]         |
| (B) frozen       (Snowflake) Lanes frozen                                  |
|                  You froze the lanes. No new steps start on any lane. ...  |
+---------------------------------------------------------------------------+
```

| Aspect | Contract |
|--------|----------|
| Header row | `HStack justify="space-between"`. Left: `Text` "Lanes" 14px/700. Right: the Freeze lanes button. |
| Freeze lanes button | `Button` `variant="outline"` `colorScheme="teal"` `leftIcon={<Snowflake aria-hidden size={16} />}`, label `Freeze lanes`, default `md` size, `aria-label` equals the visible label. Click opens the confirm; it sends nothing itself. |
| Button disabled when | The lanes are already frozen (`halted`), or nothing is running (`!queueBusy`, i.e. there is nothing to freeze). `isDisabled`, wrapped in a `Tooltip` whose text equals the visible reason line below. |
| Disabled reason (14px muted, under the header, `aria-live="polite"`) | Frozen: `Lanes are already frozen.` Nothing running: `Nothing is running, so there is nothing to freeze.` Shown only while disabled. |
| Running-now row (A) | 12px muted `Running now:` then a `Wrap spacing={2}` of `Tag size="sm"` chips, one per lane with a step in flight: `{lane} · {tool display name}`. With none: 14px muted `No lane step is running.` Always text. |
| Frozen state (B) | Replaces the running-now row's emphasis; running-now chips still show beneath it. A `Badge colorScheme="orange"` with `Snowflake` icon and the text `Lanes frozen` (`textTransform="none"`), then one 16px/400 sentence by reason (below). `role="status"`, `aria-live="polite"`. |
| Not used | No red, no spinner, no countdown, no auto-dismiss, no `setTimeout`/`setInterval`. The state is derived from the poll only. |

Frozen reason sentences (one per `laneStatus.haltReason`; the first matching reason wins, failure over freeze over modal):

| `haltReason` | Sentence |
|--------------|----------|
| `failure` | `A step failed. No new steps start on any lane. Steps already running finish on their own. Check the instrument, then press Start. A Start runs the failed step again.` |
| `freeze` | `You froze the lanes. No new steps start on any lane. Steps already running finish on their own. Press Start to resume.` |
