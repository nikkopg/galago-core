## Visual Focal Points

One unambiguous focal anchor per surface, declared explicitly:

- **Card focal point: the "Acknowledge failure…" action.** It is the ONLY solid-accent element on the
  card (the only solid `teal.500 #44518e` fill); every other card element is neutral —
  "Run Recovery" title and description are text, "Read latch" is a plain default/outline Button, the
  latch result block is neutral text, and the guid Input is a bordered outline field. Reading order
  reinforces it: card title (20px bold) → description (16px) → "Latched failure" block (16px bold
  sub-heading) → "Failure guid" field → the solid CTA at the bottom of the card.
- **Modal focal point: the guid restatement line.** The body's first sentence
  (`Acknowledge the most recent failure on this tool using guid "{guid}".`) is the modal's
  information center — the quoted guid is byte-for-byte verbatim and the line the operator must read
  before acting; nothing in the modal body competes with it (decision labels are 14px ordinary text,
  radios are small controls).
- **Modal terminal accent: "Confirm".** The solid-teal Confirm button in the footer is the modal's
  only solid-accent control and the last thing the operator touches; it stays disabled (standard
  Chakra disabled grey) until "Arm inspected?" is answered "Yes", so the accent activates exactly when
  the send becomes possible.

## Interaction Contract (UI-08 hard rules — non-negotiable, scan-enforced)

These are project constraints (PROJECT.md + `test/staticScan.test.ts`) rather than checker
dimensions, but the executor binds to them here:

1. **No timers/polling anywhere in this UI.** "Read latch" runs exactly once per click; no
   `refetchInterval` on the latch query; `RunRecoverySection.tsx` and any new client module stays in
   the `controlUiModules` no-timers list.
2. **No Enter-bound default.** The guid Input has no `onKeyDown`, no onSubmit, no `<form>` wrapper,
   no `defaultValue`/`defaultChecked`, no `autoFocus`, no `type="submit"` anywhere in
   `RunRecoverySection.tsx` or `RunControlConfirmModal.tsx`. Pressing Enter while typing the guid
   must do nothing (it may blur at most — no, it must NOT trigger any send or modal open).
3. **Initial focus on the modal is Cancel** — retained `initialFocusRef={cancelRef}`. Do not focus
   the radios, the guid field, Confirm, or the X button.
4. **Choices are born empty.** RadioGroup starts `value=""`; nothing preselected; "not chosen" is a
   real state until the operator clicks a radio.
5. **No instrument-state gating.** `tracked` stays false for STACK card buttons (buttons stay
   enabled while a STACK step runs — the server refuses, per D-09). The latch result NEVER gates or
   enables "Acknowledge failure…" (only the typed guid does), and the latch read never feeds the
   send path. `/latch/i` must not appear in `recoveryControl.ts`, `controlDecision.ts`,
   `RunControlConfirmModal.tsx`, `useRunControl.ts`.
6. **Single confirmed send path, once, never retried.** Acknowledge goes through
   `createConfirmedSender` → `tool.recoveryControl` with the completed decisions
   (`guid` from the input as-is, `arm_inspected: "yes"`), in-flight guarded; on refusal/error no
   automatic resend is performed by any UI code. GREEN `tool.recoveryControl` regex stays matched
   by ONLY `hooks/useRunControl.ts` (card must not reference the mutation).
7. **Client guid check mirrors the server validator exactly** (`recoveryActions.ts` shared function,
   zero-import) — it enables only; it is not the gate.
