<objective>
Give the operator the latched guid without polling or an implicit decision: a toolId-only
`tool.latchStatus` query that sends ONE fixed `LATCH_READ_COMMAND` through `tool.executeCommand`, a
pure `extractLatch` that tolerates unknown reply shapes, and the "Latched failure" block on the STACK
Run Recovery card — explicit "Read latch" click, read-only result, "Use this guid" that fills the input
only (D-11, D-12, D-13; OPR-03).

Purpose: the failed step's stored error (shipped Phase 3) is the primary guid surface; the latch read is
the structured secondary. The result must remain pure display data — it never gates or feeds the ack
(D-12/UI-08), and the read is a fixed-constant command so the card can never become a generic command
sender (ACK-AND-F3.md §3.3).

Output: `LATCH_READ_COMMAND` + `extractLatch` in `server/recoveryActions.ts` (appended), the
`latchStatus` query in `server/routers/tool.ts`, the card block in `RunRecoverySection.tsx`,
`test/latchStatus.test.ts`.

Task 1 is this plan's tracer: query end-to-end on a stack FakeGrpc — reply.meta_data through
extractLatch to the returned display object. Task 2 builds the card block.
</objective>
