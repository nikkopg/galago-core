<objective>
Stop an operator-aborted queue step from being re-run when the queue is next started, and lock the behavior with unit tests.

Observed at planning time (live reads of the files):
- `controller/server/utils/SqliteQueue.ts`: `complete(id)` (line 450) and `skip(id)` (line 463) set the status and run `DELETE FROM <q>_queue WHERE queue_id = ?` in one transaction. `fail(id, error)` (line 493) only sets status FAILED and leaves the row in `<q>_queue`. `startNext()` (line 112) takes the lowest-position `<q>_queue` row with no status filter and sets it STARTED, so a FAILED step is the first thing re-run on the next start.
- `controller/server/command_queue.ts` `_runBusyLoopWhileQueueNotEmpty` (line 787): `startNext()` at line 793; any throw from `executeCommand(nextCommand)` reaches the catch at line 1152, which calls `commands.fail(...)` (line 1156), sets the queue FAILED and breaks the loop. The `_runningStep` record is cleared in a `finally` immediately before that catch runs, in the same continuation.
- Every running-step Abort (ControlBar, ToolPausedModal prompt, InstrumentStopModal for "Pause queue" / Clear All / per-run delete) goes through `commandQueue.toolControl` (`controller/hooks/useRunControl.ts` sendRunning; `target: { kind: "running" }`). `toolControl` (line 429) holds the running-step snapshot `step` (queueId, runId, toolId, toolType) and the tool's reply `result` (`ToolControlResult { ok, response, message? }`, `ok` means ResponseCode SUCCESS).
- The F.A.S.T. adapter (`vendor/galago-tools/tools/fast/server.py`) ends an aborted run with ERROR_FROM_TOOL ("run aborted at N%"), so an aborted step always reaches the busy-loop failure path.

Design decision (resolved from the code, not guessed): failed-step retry is intentional upstream behavior and is kept.
- `fail` has never removed the row: same in the original `RedisQueue.fail` (commit f2721c9) and in `SqliteQueue` (commit 5a5fde5).
- The UI treats a FAILED step as still queued: `controller/components/runs/list/SwimLaneCommandComponent.tsx` computes `queued` as `queueId && (CREATED || FAILED || STARTED)` and offers Skip on it, so the operator can fix a fault and restart (retry) or Skip.
- So only operator-ABORTED steps leave the queue; every other failure behaves exactly as today.

Abort-detection signal: the queue's own record that the tool ACCEPTED an abort for that queueId. `toolControl` already knows the running step's queueId and the reply. When `action === "abort"` and `result.ok` is true, it records the queueId. The busy-loop catch then fails that step with `dequeue: true`. The signal does not parse error text, read run state or use the RunStateMonitor. A refused abort (`ok: false`) or an abort transport error does not count, because the instrument did not confirm it. Those cases keep retry-plus-Skip.

Race covered: `toolControl` awaits a `logAction` after the reply, and the step can fail before the abort reply arrives. So the abort is recorded at a point that checks `this._runningStep === step`:
- if it still matches, set the marker;
- if not, the busy loop has already recorded the step's outcome (finally and catch run synchronously in one continuation), so dequeue that queueId directly. This is a no-op if the step completed or was deleted.

Status: the aborted step stays FAILED. `RunStatus` in `controller/types/run.ts` is `"CREATED" | "STARTED" | "FAILED" | "COMPLETED" | "SKIPPED"`, with no aborted state. Adding one would change `setRunStatusWithTimestamp`, the swim-lane colors and `queued` predicate, and `getRunAttributes` in `controller/components/runs/utils.ts`. The stored error stays the tool's own reply (for the F.A.S.T. that is "run aborted at N%: ..."). The abort-and-dequeue is noted in the audit log.

UI and run history are unaffected:
- The run page, queue status and Gantt all read `commandQueue.getAll` (`SqliteQueue.all()`, from `<q>_commands`), so the aborted step stays visible as FAILED and the run still shows FAILED.
- `getPaginated` (an INNER JOIN on `<q>_queue`) has no UI caller.
- `clearCompleted` removes command records that are not in `<q>_queue`, so it now clears an aborted step the same way it clears completed and skipped steps.

Flows checked against the existing Phase 2 follow-ups:
- "Pause queue" Stop (abort then `stop`): the step is NOT removed today, so this fix covers it.
- ControlBar / ToolPausedModal Abort (no follow-up): NOT removed today, so this fix covers it.
- Clear All / per-run delete (abort then `clearAll` / `clearByRunId`): rows are already deleted, so there is no double-handling.
- Pre-existing, observed and NOT changed here: when the aborted step ends after Clear All / delete-run removed its row, `commands.fail` throws "Item N not found" from `_updateItem`, and that surfaces through `_start`'s catch. Report it in the SUMMARY as a follow-up candidate.

Out of scope, with evidence:
- Run Recovery Abort (`controller/server/recoveryControl.ts`, `tool.recoveryControl`) is allowed only when no queue step is tracking that tool. It exists for instrument runs "that no run step is tracking" (`controller/components/tools/RunRecoverySection.tsx`), which can include runs started outside this queue process. The queue has no reliable queueId link for it, so it is left unchanged: the operator still has Skip on the FAILED/STARTED card.
- Aborts made on the instrument itself are not queue-owned, so they also keep today's retry-plus-Skip behavior.

Purpose: the operator decides every recovery action (PROJECT core value). Re-running a transfer they aborted, just because the queue was restarted, is a physical action they did not choose.
Output: patched `SqliteQueue.fail` plus new `SqliteQueue.dequeue`, the abort marker in `CommandQueue`, four new queue-level tests in `controller/test/toolControl.test.ts`, and a new `controller/test/sqliteQueue.test.ts`.
</objective>
