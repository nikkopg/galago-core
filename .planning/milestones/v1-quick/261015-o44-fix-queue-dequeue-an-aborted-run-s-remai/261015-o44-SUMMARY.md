# Quick Task 261015-o44: Queue dequeue an aborted run's remainder, gate the late abort reply, and stop re-dispatching restart orphans — Summary

**Run-wide queue removal (failAndDequeueRun / dequeueFailedRun / recoverInterruptedSteps) replaces the single-row dequeue from 261015-h0q, closing T-01-08 with a three-layer identity/token/re-check gate on the late-reply path and adding restart-orphan recovery.**

## Accomplishments
- An accepted operator Abort now fails the aborted step and dequeues every other still-queued step of the same run (CREATED becomes SKIPPED, other statuses just dequeued, records kept); a queue restart then runs only the next run.
- T-01-08 closed: the late-reply branch of `_recordAcceptedAbort` is gated by three layers with no await between them — `_runningStep` identity, a new per-attempt `_failedAttempt` token (set synchronously in the busy-loop catch, cleared on every new attempt and by `_start`/`gotoCommand`/`gotoCommandByRunIndex`), and `SqliteQueue.dequeueFailedRun`'s own synchronous re-check that the row exists, `run_id` matches, status is FAILED and it is still queued. The old ungated `SqliteQueue.dequeue` single-row method is deleted entirely.
- A step left STARTED by a dead previous galago-web process is never re-dispatched: `SqliteQueue.recoverInterruptedSteps` fails every orphaned STARTED row ("interrupted by restart") and dequeues its run's remainder, run once at `CommandQueue` construction and retried in `_start` before the first busy loop (fails closed if recovery keeps failing).
- Full gates green: 235/235 unit tests (228 baseline + 7 new), `tsc --noEmit` clean, `prettier --check` clean on all five code/test files.

## Decisions Made
- Remaining steps of an aborted/interrupted run become SKIPPED (CREATED rows only) and leave the queue; records are kept and no new `RunStatus` value was added, consistent with 261015-h0q's precedent.
- The T-01-08 gate's three layers (running-step identity, `_failedAttempt` token, SqliteQueue's own transactional re-check) are evaluated with no `await` between them, so a late async reply can never race past a newer operator action.
- `recoverInterruptedSteps` only ever runs at construction (before any busy loop in this process) and in `_start` until it succeeds once, so it structurally cannot see this process's own running step; a second process sharing `queue.db` remains an unsupported configuration (T-o44-04, documented, not mitigated further).
