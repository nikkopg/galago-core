<objective>
This closes milestone audit gap INT-01 (FLOW-d, UI-06 x QUE-01) and the pending todo "Queue errors
'Item N not found' after clear during abort". Both have one root cause. Clear All (`clearAll`) and
delete-run (`clearByRunId`) delete a step's row even while it is STARTED. The busy-loop catch then
calls `failAndDequeueRun` (accepted abort) or `fail` (plain failure). Both go through
`_updateItem` -> `find`, which throws `Item N not found`. The throw escapes through `_start`'s catch,
so the queue goes FAILED and shows a raw internal error after a clean, confirmed operator action.

Purpose: the operator removed the running step. That removal is the handling, so the queue must not
invent an error or keep going on its own.

Output: a typed "row gone" result from `SqliteQueue.fail` / `failAndDequeueRun`, a removed-row
branch in the busy-loop catch, deterministic race tests (UI sequencing primitive -> real router ->
real CommandQueue -> real SQLite), and the todo moved to completed.

Planner decisions. No CONTEXT.md exists for this quick task. These are resolved from the code at
planning time:

- **Q1: where the missing row is tolerated.** In `SqliteQueue`, as a return value, decided inside
  the same better-sqlite3 transaction as the update. There is no check-then-act gap and no
  error-message matching.
  - `fail` resolves `Promise<boolean>`: false means the row no longer exists and nothing changed.
  - `failAndDequeueRun` resolves `Promise<number[] | false>`. This mirrors the existing
    `dequeueFailedRun` convention.
  - `_updateItem` and `find` keep throwing for every other caller (`complete`, `skip`,
    `_dequeueRunRemainder`, `recoverInterruptedSteps`, `startNext`).
  - Rejected alternative: an existence check in CommandQueue before the call. That puts an await
    between check and write.
  - Rejected alternative: catching the thrown error by message. That is string matching.
- **Q2: the resulting queue state.** When the row is gone, the queue does not go FAILED, sets no
  `this.error` and sends no failure notification. It logs "Step Removed While Running" (warning,
  with the step's own error text so nothing is lost), sets OFFLINE and leaves the busy loop.
  Justification against today's behavior when the follow-up lands *after* the step ended (no race):
  - Clear All: `CommandQueue.clearAll` calls `clearError()`, so the non-racing end state is already
    "no error". Setting the step's error after the operator's Clear All would bring back an error the
    operator just cleared. Not-FAILED makes both orders converge.
  - Stopped, not READY: READY lets `enqueueRun` auto-start the queue. After a delete-run, that would
    dispatch the remaining runs without an explicit Run press. OFFLINE is how the sibling Pause-queue
    flow (D-18 + stop) and a drained queue end. In both orders the queue dispatches nothing more
    until the operator presses Run, which keeps D-18's "an aborted step stops the queue".
  - When the row still exists, nothing changes: FAILED + step error + "Command Failed" + notify.
    This includes the D-18 Pause-queue flow, because `stop()` deletes no rows.
- **Q3: late abort reply (T-01-08).** Confirmed already safe. `dequeueFailedRun` selects the row
  first and returns false when it is missing, before any `_updateItem`/`find` call.
  `_recordAcceptedAbort` then logs "Aborted Run Dequeue Skipped", and toolControl wraps it in
  try/catch anyway. The existing unit case "A missing id" covers it. Task 2 adds an end-to-end
  assertion. No code change. Leave `_failedAttempt` handling as is: queue_id is AUTOINCREMENT and
  never reused, so layer (c) is sufficient.
- **Consequence, documented and tested.** A step whose tool call *succeeds* after its row was removed
  throws from `complete()` inside `executeCommand`, then reaches the same catch. With `fail`
  returning false, it takes the removed-row branch. `complete()` itself is not changed (every Tool
  Box path shares it). That branch's log line then carries the internal `complete()` message as
  `stepError`, which is acceptable for a log line. The queue-visible surfaces are clean.
- **Out of scope (do not change):**
  - `complete`/`skip` semantics.
  - The Tool Box `stop_run` + Clear All path (`handleRunStop`).
  - `_updateItem`/`find`.
  - The router not awaiting clearAll/clearByRunId.
  - UI components.
  - `.planning/v1-MILESTONE-AUDIT.md` and STATE.md (the orchestrator owns them).
  - `vendor/galago-tools` (submodule).
</objective>
