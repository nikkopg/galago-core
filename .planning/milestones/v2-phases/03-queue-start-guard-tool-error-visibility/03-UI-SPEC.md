# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope.** Brownfield. Five existing surfaces get one small change each; no new screens, no new tokens, no
new dependencies. Everything reuses Chakra UI 2.8.2, the existing `themes/customTheme.ts` and the values
already present in the files named below. `--auto` run: every open choice was resolved to the option closest to
the existing code and to `03-CONTEXT.md`, and is marked **[assumed]** where it is not a locked decision.

| # | Surface | File | Change |
|---|---------|------|--------|
| S1 | Run confirmation modal | `controller/components/runs/status/QueueStatuscomponent.tsx` | Add a read-only "what this Start will run" summary (QUE-08) |
| S2 | Run page error banner | `controller/components/runs/RunsComponent.tsx` (`ErrorBanner`) | Show the tool's own text and real code; re-arm after dismiss (ERR-02, ERR-04) |
| S3 | Step card | `controller/components/runs/list/SwimLaneCommandComponent.tsx` | Show the stored error on FAILED and skipped-after-failure cards (ERR-03) |
| S4 | Run row outcome | `controller/components/runs/RunsComponent.tsx` (`renderRunsList`) + `utils.ts` | A non-success badge and progress colour for "completed with skipped failure" (ERR-05) |
| S5 | Queue Start Ignored | none (Logs only) | No UI. An ignored Start is silent to the operator by decision D-02 (no toast) |

**Hard interaction constraints (UI-08, carried from v1 D-07, apply to S1 and S2).** No timer (`setTimeout`,
`setInterval`, countdown), no pre-selected option, no `autoFocus`, no `defaultValue`, no `<form>`, no
Enter-bound default, no `StopRunModal`/`InstrumentStopModal` reuse in `QueueStatuscomponent.tsx`, no new UI test
dependency (no jsdom, no React Testing Library). Behaviour is proven by pure-logic modules plus static scans in
`test/staticScan.test.ts`.

## Surface specifications

### S1. Run confirmation modal (QUE-08, D-05..D-08)

Keep exactly as today: `Modal` (default size), header "Warning", `ModalCloseButton`, the sentence "Make sure
instruments are not unintentionally in simulation mode.", footer `Button colorScheme="teal" mr={3}` "Accept"
then `Button variant="ghost"` "Cancel". Do not reorder, rename, add a button, add `initialFocusRef`, or change
which element Chakra focuses first (today it is the close button). Nothing is pre-selected; Enter does not
trigger Accept.

Add inside `ModalBody`, below the existing sentence, a `VStack align="stretch" spacing={2} mt={4}` with
read-only `Text` lines (16px / 400):

| Condition (from `summarizeQueuedStart` over the `commandQueue.commands` rows) | Line copy |
|-------|-----------|
| N >= 1 | `This Start will run {N} queued step(s) from {M} run(s).` Singular/plural resolved: `1 queued step`, `{N} queued steps`, `1 run`, `{M} runs` |
| F >= 1 and N > 1 | `{F} of them failed before and will be retried first.` |
| F = 1 and N = 1 | `It failed before and will be retried first.` |
| S >= 1 (a STARTED row exists) **[assumed, A6]** | `{S} step(s) still running. A Start is ignored until it ends.` (14px, `color="gray.500"`) |
| N = 0 | `The queue is empty.` (Accept still behaves as today) |
| Always, last line, 14px, `color="gray.500"` | `Counts refresh every second. Logs list the exact steps this Start ran.` |
| Query has no data yet (first load) | `Checking the queue...` (14px, `color="gray.500"`); Accept stays enabled and behaves as today |
| Query errored | `Could not read the queue. Logs list the steps this Start ran.` (14px, `color="gray.500"`); Accept stays enabled |

`N` counts rows that will run (CREATED + FAILED, not STARTED), `F` counts FAILED, `M` counts distinct `runId`
of the counted rows. Data source is the `commandQueue.commands` query (joined to the queue) at a 1 s
`refetchInterval`, not `getAll`, so a dequeued FAILED row is never promised as a retry (research Pitfall 2; the
existing `getAll` poll is kept for `hasCommandsToClear`). Summary text is assembled by the pure helper, never in
JSX string math.

Tool/Run text is never interpolated into this modal, so it cannot carry tool-supplied markup.

### S2. Run page error banner (ERR-02, ERR-04, D-12..D-16)

Keep the existing `Alert status="error" variant="left-accent" mb={2}`, `AlertIcon`, title "Error", code `Badge
colorScheme="red"`, `Details` button (`size="sm"`, `colorScheme="red"`, `variant="outline"`) and
`CloseButton`. Changes:

- **Message.** `AlertDescription` shows `describeQueueError(getError.data).message`, the full tool-composed
  text. It is selectable text, `whiteSpace="pre-wrap"`, `wordBreak="break-word"`, inside the `maxH="160px"`
  `overflowY="auto"` region. It is never truncated by `noOfLines` and never replaced by a generic sentence when
  the tool sent text. For the four generic codes the banner shows the generic sentence followed by `Tool said:
  <text>` exactly as composed on the server (D-11); the UI does not recompose it.
- **Code badge.** Shows the real code name (`INVALID_ARGUMENTS`, `NOT_READY`, `ERROR_FROM_TOOL`, ...). Hidden
  when the error carries no code (non-tool errors). Never `UNKNOWN`, never `SUCCESS`; a SUCCESS reply with an
  error message arrives as `ERROR_FROM_TOOL` (D-14).
- **Empty-text fallback** (message string empty or absent): `The command failed and the tool sent no message.
  Open Details for the raw error.`
- **Dismiss.** `CloseButton` gets `aria-label="Dismiss error"` and stores `dismissedSeq = getError.data.seq`.
  Banner visibility is `shouldShowErrorBanner(queueState, errorData, dismissedSeq)`: shown when the queue state
  is FAILED, an error exists and `seq !== dismissedSeq`; a payload without `seq` always shows. A later failure
  carries a larger `seq` and shows the banner again with no operator action. Dismissing never clears the error
  or restarts anything.
- **Details modal** (`ErrorModal`) is unchanged; its JSON now comes from the plain-object `getError` payload so it
  no longer shows `{}`.
- No toast is added. The banner stays inline at the top of the run list as today.

### S3. Step card error text (ERR-03, D-17)

In `SwimLaneCommandComponent`, render `stepErrorText(command)` (null for any status other than FAILED, or
SKIPPED carrying a stored error). Placement: `CommandImage` and the error `Text` share one `HStack` row inside
the existing inner `VStack`: image left in a non-shrinking `Box` (`flexShrink={0}`), text right with `flex="1"`
and `minW={0}`, the row centred when there is no error. The unchanged sticky command-label `Box` follows the row;
DOM order stays image, text, label. The row is as tall as the image block (64/65px), so the 3-line text (63px)
adds no height and the card never scrolls. History: the first placement (text stacked under the image)
overflowed the card by 67px and the pinned label covered the first error line (UAT test 3, gap G-03-3,
`.planning/debug/step-card-error-overflow.md`); amended by 03-07. Do not change the card size or the sticky
label.

| Status | Copy | Style |
|--------|------|-------|
| FAILED | `{stored message}` | `Text fontSize="sm"` (14px / 400), colour per table in Color, `noOfLines={3}`, `whiteSpace="normal"`, `wordBreak="break-word"`, `textAlign="left"`, `userSelect="text"`, `title={full text}` |
| SKIPPED with stored error | `Skipped after failure: {stored message}` | same style, orange colours |
| COMPLETED, STARTED, CREATED, or SKIPPED without error | nothing rendered (a retried-then-COMPLETED row keeps a stale error in storage; it must not show) | n/a |

- `whiteSpace="normal"` is required because `SwimLaneComponent` wraps cards in a `nowrap` parent.
- Full text is available through the native `title` tooltip and the banner; no new expand control.
- A SKIPPED card that carries an error does **not** get the 0.55 `opacity` of plain COMPLETED/SKIPPED cards
  (opacity 1, background unchanged) so the failure text stays legible **[assumed]**. A plain operator Skip keeps
  today's dimmed look and shows no text.
- The `CheckCircle` icon stays under `status === "COMPLETED"` only (one occurrence). A FAILED card keeps its red
  background and shows no check.
- The card shows message text only; it never shows a code (the persisted error has no code after the SQLite
  round trip).
- Text comes from the persisted row, so it survives a dismissed banner and a galago-web restart.

### S4. Run row outcome (ERR-05, D-18, D-19)

`getRunAttributes` delegates to the pure `deriveRunOutcome(run.Commands)`; `RunsComponent` passes the run's
commands array (today it passes one command, so the status is always `CREATED`) and drops the
`status !== cmdInfo?.status` memo guard. `RunStatus` in `types/run.ts` is not widened.

For the outcome `COMPLETED_WITH_SKIPPED_FAILURE` **[assumed name]**:

| Element | Contract |
|---------|----------|
| Badge | `Badge colorScheme="orange" variant="subtle"`, text `Skipped failure`, `ml={2}`, placed right after the run name inside the existing name `HStack`; `title="Completed, but a failed step was skipped, not completed."`; optional leading `AlertTriangle` 12px |
| Progress bar | `colorScheme="orange"` instead of `teal` (the `hasStripe isAnimated` props and value formula are unchanged) |
| Success treatment | none: no green, no teal, no check icon, not counted by the existing "Completed" stat (already true) |

A plain operator Skip with no stored error keeps today's outcome. A FAILED run keeps `FAILED`. No other outcome
renders a new badge, so existing run rows look the same.

### S5. Ignored Start (QUE-07, D-02)

No visible change. `restart` resolves normally, no toast, no banner. The queue keeps showing the `Pause queue`
button because the state stays BUSY. The record is the `Queue Start Ignored` warning in Logs. D-04: after
`Pause queue`, `Start` pressed while a step is still in flight is ignored until the step ends; the optional
"still running" line in S1 is the only hint.

## UI Considerations

Probe: `ui-consideration-probe.cjs` over S1-S4 (`--auto`; kinds confirmed by re-reading each surface, S2 gained
`empty` and `populated`). 30 applicable: 24 resolved (explicit), 5 resolved (backstop), 1 unresolved. Copy for
empty/error states lives in the Copywriting Contract; rows here reference it.

### Resolved (explicit) — truths

- S1 empty: with no rows in the `commands` query the modal shows "The queue is empty." and Accept/Cancel behave as today.
- S1 loading: while the `commands` query has no data the modal shows "Checking the queue..." and Accept stays enabled.
- S1 error: a failed `commands` query shows "Could not read the queue. Logs list the steps this Start ran." and does not disable Accept.
- S1 populated: with N queued rows from M runs the modal shows "This Start will run N queued step(s) from M run(s)." from `summarizeQueuedStart`.
- S1 partial: STARTED rows are counted separately as "{S} step(s) still running. A Start is ignored until it ends." and not counted as "will run".
- S1 zero-one-many: singular/plural copy for 1 vs N steps and 1 vs M runs; the failed-retry line is omitted when F = 0 (unit-tested in `queuedStartSummary.test.ts`).
- S1 overflow: the summary is counts only (no per-row list), so its length is bounded regardless of queue size.
- S2 empty: with no error, or queue state not FAILED, `shouldShowErrorBanner` returns false and no banner renders.
- S2 populated: the banner shows when state is FAILED, an error exists and `seq !== dismissedSeq`; it reappears on the next failure seq (unit-tested in `queueError.test.ts`).
- S2 loading: before the first `getError` response the banner does not render (no placeholder).
- S2 error: when the tool text is empty `describeQueueError` returns the fallback copy, never an empty string, and the badge is never `SUCCESS`.
- S2 long-text: the full message renders with `whiteSpace="pre-wrap"` and `wordBreak="break-word"` in a region with `maxH` 160px and vertical scroll; never `noOfLines`.
- S3 empty: `stepErrorText` returns null for a row without a stored error and the card renders no error `Text`.
- S3 loading: the card renders from the already-loaded run commands; no extra fetch, no loading state.
- S3 error: an unreadable stored error value (non-Error, string, `{message}`) is normalised by `stepErrorText`; it never throws.
- S3 populated: a FAILED card shows its stored error message; a SKIPPED card with an error shows "Skipped after failure: <text>".
- S3 partial: a COMPLETED, STARTED or CREATED row that kept a stale error shows no error text (`stepErrorText` returns null).
- S3 zero-one-many: each card shows at most its own one error message.
- S3 long-text: the error `Text` uses `noOfLines={3}`, `whiteSpace="normal"`, `wordBreak="break-word"`, and a `title` carrying the full text.
- S4 empty: a run with no commands derives no special outcome and shows no "Skipped failure" badge.
- S4 loading: the outcome is derived from the already-loaded `run.Commands`; no loading state.
- S4 error: `deriveRunOutcome` tolerates missing or non-array commands and returns a non-success default.
- S4 populated: a run with any SKIPPED step carrying an error derives `COMPLETED_WITH_SKIPPED_FAILURE`, an orange "Skipped failure" badge and an orange Progress bar, never green/teal and never a check icon (unit-tested in `runOutcome.test.ts`).
- S4 zero-one-many: one or several skipped-with-error steps yield the same single badge per run.

## Accessibility and interaction notes

- The banner keeps Chakra's `role="alert"`, so a re-armed banner on a new failure is announced.
- Every new piece of status information pairs colour with text (see Color rules).
- S1 adds only static text: no new focusable element, no new key handler. Focus order is unchanged: close
  button, Accept, Cancel.
- Contrast: the S3 and S4 colour pairs in the Color section use the 800/900 shades on 200 backgrounds in light
  mode and the 50/200 shades on 800 backgrounds in dark mode (all pairs above 4.5:1 by Chakra's palette).
- Static-scan cases to add (new `it` blocks only; existing ones are not edited): the S1 modal reads the
  `commands` query, calls `summarizeQueuedStart`, keeps the existing warning sentence, and contains none of
  `setTimeout(`, `setInterval(`, `autoFocus`, `defaultValue`, `<form`, `StopRunModal`; `RunsComponent.tsx` no
  longer contains `isErrorVisible` and uses `dismissedSeq` and `shouldShowErrorBanner`; the step card has one
  `CheckCircle` under `status === "COMPLETED"` and renders `stepErrorText` with `whiteSpace="normal"` and
  `noOfLines`; the outcome helper never maps `COMPLETED_WITH_SKIPPED_FAILURE` to a green or teal scheme; new
  components do not use `dangerouslySetInnerHTML`.
