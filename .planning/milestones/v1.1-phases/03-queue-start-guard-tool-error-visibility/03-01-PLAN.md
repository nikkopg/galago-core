<objective>
Fix F5's real defect and make every Start auditable, server side. A Start, restart or enqueue while the
busy loop runs must never dispatch the in-flight row a second time (QUE-07). Every Start that is not
ignored must log the queue_ids and run_ids it will run (QUE-08, server half). Retry-after-failure stays
exactly as it is (QUE-09).

Purpose: double dispatch of a physical instrument step is the only way the code can run the same row
twice (F5-ROOT-CAUSE.md section 5, candidate D). The guard closes it at the one method every entry point
uses. The audit line explains a multi-row Start, which is the real cause of the F5 report.

Output: a guarded `_start`, a synchronous read-only `SqliteQueue.queuedRowsSync()`, a pure
`server/queueStartListing.ts`, and `test/queueStartGuard.test.ts`.

Task 1 is this phase's tracer: the thinnest end-to-end path from the operator's entry point (tRPC
`restart`, which the Run confirmation's Accept calls) through `_start` and the busy loop to the fake
tool and the audit log. Task 2 expands it with the "what this Start will run" listing.
</objective>

## Deviations and resolved assumptions (recorded, not silent)

- **D-07 read is synchronous (deviation from the obvious `await this.commands.getPaginated()`):** the
  listing is read with the new synchronous `queuedRowsSync()`. An `await` between the guard and
  `this._runningPromise = ...` would let two same-tick `_start()` calls both pass the guard (research
  Pitfall 1). A same-tick double-start test pins this. Adding a read-only method does not touch any
  method D-09 freezes (research Open Question 1, recommended answer).
- **D-01 "caller-visible reason":** the ignored-start details carry a fixed reason sentence plus
  `source=operator|enqueue`, `inFlightQueueId` and `inFlightRunId`. `_start` gains an optional
  `source` parameter (default `"operator"`), so every existing `_start()` call and test is unchanged.
- **Listing cap (research A4):** at most 50 rows are listed, then `; ... and N more`.
- **Counting rule (matches the client summary in 03-03):** "will run" counts CREATED and FAILED rows;
  every queued row is still listed with its status.

## Assumption-delta decision

<assumption_delta_decision>
Detector: `assumption-delta scan 3` returned detected=true, one `pluralization` signal on the word
"second" ("does not dispatch that row a second time").
Primary noun: the queue row (queue_id) dispatched by the single global CommandQueue busy loop.
Decision: no-change. "Second" names a repeated dispatch of the same row that this phase forbids. It does
not add a second queue, owner or identity. The single in-memory busy-loop owner (`_runningPromise`)
stays the only dispatcher, and this plan enforces that.
Invariant test (suggested companion, adopted): queueStartGuard.test.ts asserts executeCommand is called
exactly once per in-flight row for every entry point (restart router, same-tick _start, enqueueRun).
</assumption_delta_decision>
